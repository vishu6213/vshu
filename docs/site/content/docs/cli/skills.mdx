Vshu ships **skills** that agents install into their skill directories. Public install packages are **hybrid discovery stubs**: short `SKILL.md` files that tell the agent _when_ to engage Vshu and how to load the full guide from the running CLI. Command flags live in the binary so they cannot drift from the app version.

## Installable Vshu skills

Use `npx skills add` with the public Vshu repo and the skill name. Default agent setup usually installs `vshu-cli`, `vshu-computer-use`, and `orchestration`.

## Hybrid stubs vs the live guide

After `npx skills add`, agents see a short stub that says:

1. Resolve the CLI executable for this session (`VSHU_CLI_COMMAND`, `vshu-dev`, Linux `vshu-ide`, else `vshu`).
2. Load the full guide: `vshu skills get <topic>` (or `--full` for the long guide).
3. Prefer `--json` and do not invent flags from memory.

```bash
vshu skills list
vshu skills get vshu-cli
vshu skills get orchestration --references
vshu skills get orchestration --reference recovery-and-cleanup
vshu skills get orchestration --full
vshu skills get vshu-linear --json
```

A guide's action gates name conditional references. `--reference <name>` prints one of them alone, so an agent pays for the kernel plus that document instead of the whole package; `--references` lists the names. The name may be bare (`recovery-and-cleanup`) or spelled as the guide writes it (`references/recovery-and-cleanup.md`). `--full` still prints the kernel plus every reference.

Add `--json` when an agent needs deterministic output for automation. `skills show` is an alias for `skills get`.

## Keep skills up to date

Vshu updates its own skills itself, with no `npx`, Git, Node or network. A copy counts as Vshu's untouched copy when its folder holds only `SKILL.md` and that file matches a version Vshu has shipped. Only those copies are rewritten, in place (the shared `~/.agents/skills/<name>` or a real folder in an agent's skills folder such as `~/.claude/skills/<name>`). Anything else is left alone and reported: **You've changed this copy**, or **A different skill already uses this name**. Vshu never deletes a folder it did not create.

When this Vshu build ships a newer version of a skill you installed, the app:

- Shows an **update available** nudge and badge. Update only touches locations that already hold the skill; it never adds the skill for another agent.
- Opens **Update skills**, which lists every location and what Update does there: **No change**, **Will update**, **Will link**, or **Left alone** with the reason. A copy left alone has a **Replace** choice (off by default); Replace first moves that copy to `~/.agents/.vshu-skill-backups/`, then puts Vshu's copy in its place.
- Runs exactly the plan you reviewed: if a folder changed after you opened the dialog, that skill reports **Changed since you reviewed it** and nothing is written there.
- Shows the result per skill, for example `Updated · 1 left alone: You've changed this copy`, and a status-bar segment while it runs.

This covers skills installed on this computer. The app does not check WSL projects, SSH hosts or paired Vshu servers yet; run `vshu skills update` there.

On headless hosts (SSH, containers, CI, `vshu serve`) use the CLI. It runs the same planner on the machine that runs it and does **not** need a running Vshu app:

```bash
vshu skills install                                      # list installable names
vshu skills install --skill vshu-cli --skill orchestration
vshu skills install --skill vshu-cli --agent claude,codex
vshu skills update --all --dry-run                       # what would change, and the plan digest
vshu skills update --all
vshu skills update --all --force                         # also replace copies left alone (backup kept)
```

- Default scope is **global**; pass `--local` for the current project only (Vshu links only into agent folders the project already has).
- Targets the agents Vshu detects on the host plus the shared `.agents/skills` folder. Use `--agent <name>[,<name>…]` to choose (the skills CLI's keys such as `claude-code` still work), or `--agent universal` for the shared folder alone.
- `update` only touches locations that already hold the skill; `install` adds it, including for newly detected agents.
- `--dry-run` prints the plan and its digest without writing. A real run plans again and writes only while the plan still matches.
- `--json` works for dry runs and real runs. The exit code is 1 when a location failed or changed during the run; folders left alone are warnings.

## Install and delete from the Skills page

When an in-app install asks for a workspace target, search the picker by workspace name or by kind (**worktree** / **folder**). The agent picker separates directories Vshu always includes from additional agent directories you can select, so you can review the exact installation targets before continuing.

To remove a scanned skill, open its actions menu and choose **Delete…**. For several skills, open the page's **More actions** menu, choose **Delete skills…**, and select the eligible results. Vshu explains why a copy cannot be deleted—for example because it is bundled, plugin-managed, read-only, or outside a removable skill folder—before you confirm. This is separate from **Manage installs**, which manages copies installed from shared links.

## Share private skills between hosts

Open **Skills → Share skills** to publish one skill or a bundle behind one unlisted, revocable link. Publishing requires your Vshu account. Review the included files, scripts, executables, digest, and optional release notes before you publish; each published version is immutable, so later local edits do not silently change what recipients install.

Anyone with an active link can inspect and install the shared skills without signing in, so treat the link like a credential. A recipient reviews the exact version, chooses all or a subset of its skills, then selects global or workspace scope on this computer, a paired Vshu runtime, WSL, or an SSH host. Existing modified skills default to **Keep local**. Use **Skills → Manage installs** to update, roll back, or remove copies Vshu installed, and **Settings → Share Skills** to copy or revoke your active links. Revoking a link blocks future access but does not remove copies already installed.

Agents can publish an explicitly named set from the CLI after you enable the separate, default-off **Settings → Share Skills → Allow agents and the Vshu CLI to publish skill links** permission:

```bash
vshu skills installed --json
vshu skills share --skill frontend --skill testing --bundle-name "Team Toolkit" --json
```

`skills installed` returns safe selectors without exposing local paths. `skills share` accepts exact discovery IDs or unambiguous names; it does not accept arbitrary paths or `--all`.

## Discovery sources

Vshu's skill UI scans installed skill homes for Claude, Codex, Agent Skills, and **OMP** (`~/.omp/agent/skills`), so skills placed there show up without a manual symlink.

## Add your own skills

Any repo with a `skills/<name>/SKILL.md` file can be installed via `npx skills add`. Point your agent at internal repos to give it company-specific powers.

## MCP servers

Model Context Protocol (MCP) servers expose external tools to compatible agents. Register MCP endpoints under [Settings → Integrations → MCP](/docs/settings); those tools appear inside agent CLIs that support MCP.
